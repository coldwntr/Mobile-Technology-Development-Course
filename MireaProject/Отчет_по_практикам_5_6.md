# Отчет по практикам №5 и №6 для финального Android-проекта

## Общая идея проекта

В финальном проекте я объединил результаты нескольких практических работ в одно Android-приложение на Kotlin с использованием Jetpack Compose. Для практик №5 и №6 я перенес в итоговый модуль те части, которые связаны с аппаратными возможностями устройства и хранением данных.

Структурно приложение построено как набор экранов, переключаемых через нижнюю навигацию. Это позволяет показать на защите, что все задания собраны в одном проекте, но логически разделены по темам.

Основная точка входа в приложение находится в файле `MainActivity.kt`, где в `Scaffold` создана нижняя панель навигации:

### 1. Работа с акселерометром

По практике требовалось использовать датчики устройства и получать данные в реальном времени. В финальном проекте я реализовал экран работы с акселерометром. Для этого я получил `SensorManager`, нашел датчик типа `TYPE_ACCELEROMETER`, зарегистрировал слушатель и начал получать значения по трем осям.

```kotlin
@Composable
fun SensorSection() {
    val context = LocalContext.current
    val sensorManager = remember {
        context.getSystemService(Context.SENSOR_SERVICE) as SensorManager
    }
    val accelerometer = remember {
        sensorManager.getDefaultSensor(Sensor.TYPE_ACCELEROMETER)
    }

    var xValue by remember { mutableFloatStateOf(0f) }
    var yValue by remember { mutableFloatStateOf(0f) }
    var zValue by remember { mutableFloatStateOf(0f) }

    DisposableEffect(accelerometer) {
        if (accelerometer == null) {
            onDispose { }
        } else {
            val sensorListener = object : SensorEventListener {
                override fun onSensorChanged(event: SensorEvent) {
                    xValue = event.values[0]
                    yValue = event.values[1]
                    zValue = event.values[2]
                }

                override fun onAccuracyChanged(sensor: Sensor?, accuracy: Int) {
                }
            }

            sensorManager.registerListener(
                sensorListener,
                accelerometer,
                SensorManager.SENSOR_DELAY_UI
            )

            onDispose {
                sensorManager.unregisterListener(sensorListener)
            }
        }
    }
}
```

### Объяснение кода

1. `getSystemService(Context.SENSOR_SERVICE)` получает доступ к аппаратным датчикам телефона.
2. `getDefaultSensor(Sensor.TYPE_ACCELEROMETER)` выбирает акселерометр.
3. `SensorEventListener` нужен для чтения новых значений датчика.
4. В `onSensorChanged` приходят значения `X`, `Y` и `Z`.
5. `registerListener` запускает получение данных.
6. `unregisterListener` вызывается при уничтожении экрана, чтобы не было утечки ресурсов.

После получения значений я не просто вывожу числа, а интерпретирую положение телефона. Это делает экран более наглядным.

```kotlin
val phonePosition = when {
    accelerometer == null -> "Акселерометр не найден"
    zValue > 7f -> "Телефон лежит экраном вверх"
    zValue < -7f -> "Телефон лежит экраном вниз"
    xValue > 4f -> "Телефон наклонён влево"
    xValue < -4f -> "Телефон наклонён вправо"
    yValue > 4f -> "Телефон наклонён вниз"
    yValue < -4f -> "Телефон наклонён вверх"
    else -> "Телефон почти в ровном положении"
}
```

### Что я сделал по сути

Я преобразовал сырые данные акселерометра в понятный для пользователя результат. На защите можно сказать, что по трем осям ускорения определяется примерное положение устройства в пространстве.

### 2. Работа с разрешениями

```xml

```

Также я сделал вспомогательные функции проверки разрешений:

```kotlin
fun hasPermission(context: Context, permission: String): Boolean {
    return ContextCompat.checkSelfPermission(
        context,
        permission
    ) == PackageManager.PERMISSION_GRANTED
}

fun permissionText(context: Context, permission: String): String {
    return if (hasPermission(context, permission)) {
        "разрешено"
    } else {
        "не разрешено"
    }
}
```

### Объяснение

Перед запуском камеры или записи звука приложение сначала проверяет, выдано ли разрешение. Если нет, то вызывает системный запрос через `ActivityResultContracts.RequestPermission()`. Это соответствует современной модели безопасности Android.

### Как это работает

1. По нажатию кнопки приложение проверяет разрешение на камеру.
2. Если разрешение есть, создается файл для будущего изображения.
3. Для безопасной передачи файла в системную камеру используется `FileProvider`.
4. Затем вызывается `ActivityResultContracts.TakePicture()`.
5. После съемки URI изображения сохраняется в состоянии экрана.
6. Готовое фото показывается пользователю через `ImageView`.

Функция создания файла:

```kotlin
fun createImageFile(context: Context): File? {
    val picturesDirectory = context.getExternalFilesDir(Environment.DIRECTORY_PICTURES)
        ?: return null
    val timeStamp = SimpleDateFormat("yyyyMMdd_HHmmss", Locale.getDefault()).format(Date())

    return File(picturesDirectory, "camera_$timeStamp.jpg")
}
```

### Зачем нужен `FileProvider`

Начиная с новых версий Android нельзя просто передавать обычный путь к файлу в другое приложение. Поэтому я добавил `FileProvider` в `AndroidManifest.xml` и файл `paths.xml`.

```xml
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="${applicationId}.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/paths" />
</provider>
```

```xml
<paths xmlns:android="http://schemas.android.com/apk/res/android">
    <external-files-path
        name="external_files"
        path="." />
</paths>
```

Я реализовал безопасную съемку фото с сохранением результата в файловую систему приложения и отображением результата на экране.

## Практика №6. Хранение данных в Android

Практика №6 посвящена сохранению данных: `SharedPreferences`, файлам и базам данных. В финальном проекте я интегрировал две основные части этой практики:

1. Сохранение пользовательских данных в `SharedPreferences`.
2. Создание и сохранение файлов во внутреннем хранилище приложения.

## 1. Экран профиля и SharedPreferences

По заданию методички нужно было сохранить номер группы, номер по списку и любимый фильм или сериал, чтобы после повторного запуска приложения эти данные восстанавливались автоматически. В моем финальном проекте эта идея реализована на экране `Профиль`. Я расширил задание и добавил еще поле `Имя`.

### Листинг сохранения данных

```kotlin
private const val PROFILE_PREFERENCES = "profile_preferences"
private const val KEY_NAME = "name"
private const val KEY_GROUP = "group"
private const val KEY_NUMBER = "number"
private const val KEY_MOVIE = "movie"
```

```kotlin
Button(
    modifier = Modifier.fillMaxWidth(),
    onClick = {
        val preferences = context.getSharedPreferences(
            PROFILE_PREFERENCES,
            Context.MODE_PRIVATE
        )

        preferences.edit()
            .putString(KEY_NAME, name)
            .putString(KEY_GROUP, group)
            .putString(KEY_NUMBER, number)
            .putString(KEY_MOVIE, movie)
            .apply()

        savedText = buildProfileText(name, group, number, movie)
        Toast.makeText(context, "Профиль сохранён", Toast.LENGTH_SHORT).show()
    }
) {
    Text(text = "Сохранить")
}
```

### Листинг восстановления данных

```kotlin
LaunchedEffect(Unit) {
    val preferences = context.getSharedPreferences(
        PROFILE_PREFERENCES,
        Context.MODE_PRIVATE
    )

    name = preferences.getString(KEY_NAME, "") ?: ""
    group = preferences.getString(KEY_GROUP, "") ?: ""
    number = preferences.getString(KEY_NUMBER, "") ?: ""
    movie = preferences.getString(KEY_MOVIE, "") ?: ""
    savedText = buildProfileText(name, group, number, movie)
}
```

### Объяснение

1. Я создал отдельный файл настроек `profile_preferences`.
2. Для каждого поля ввода задал свой ключ.
3. При нажатии кнопки данные сохраняются через `edit()` и `apply()`.
4. При открытии экрана срабатывает `LaunchedEffect(Unit)`, который читает сохраненные значения.
5. Благодаря этому после повторного запуска приложения пользователь видит те же данные, что вводил раньше.

### Почему выбрано именно это решение

`SharedPreferences` хорошо подходят для небольших пользовательских настроек и анкетных данных. Для этого не нужна база данных, потому что структура простая и хранится как пары `ключ-значение`.

### Дополнение к базовому заданию

В методичке указаны три поля, а в финальном проекте я сделал четыре:

1. Имя.
2. Группа.
3. Номер по списку.
4. Любимый фильм или сериал.

Такое расширение не нарушает задание, а делает экран более завершенным и удобным для демонстрации.

## 2. Работа с файлами во внутреннем хранилище

Следующая часть практики №6 связана с хранением файлов. В финальном проекте я сделал экран `Работа с файлами`, на котором можно создать текстовую заметку и сохранить ее во внутреннее хранилище приложения.

### Как устроен экран

На основном экране показывается список уже созданных файлов. Для создания новой заметки используется `FloatingActionButton`, которая открывает диалоговое окно с вводом имени файла и текста.

```kotlin
@Composable
fun FileWorkScreen(innerPadding: PaddingValues) {
    val context = LocalContext.current
    val files = remember { mutableStateListOf<String>() }
    var showDialog by remember { mutableStateOf(false) }

    fun refreshFiles() {
        files.clear()
        files.addAll(context.fileList().sorted())
    }

    LaunchedEffect(Unit) {
        refreshFiles()
    }
}
```

### Листинг кнопки создания

```kotlin
FloatingActionButton(

        showDialog = true
    },
    modifier = Modifier
        .align(Alignment.BottomEnd)
        .padding(16.dp)
) {
    Text(
```

### Листинг сохранения файла

```kotlin
CreateFileDialog(
    onDismiss = {
        showDialog = false
    },
    onSave = { fileName, noteText ->
        context.openFileOutput(fileName, Context.MODE_PRIVATE).use { stream ->
            stream.write(noteText.toByteArray())
        }

        showDialog = false
        refreshFiles()
        Toast.makeText(context, "Файл сохранён", Toast.LENGTH_SHORT).show()
    }
)
```

### Листинг диалога ввода

```kotlin
@Composable
fun CreateFileDialog(

                    value = fileName,

                    onValueChange = { noteText = it },
                    label = { Text(text = "Текст заметки") }
                )
            }
        }
    )
}
```

### Объяснение кода

1. `context.fileList()` получает список файлов, созданных приложением.
2. `openFileOutput(fileName, Context.MODE_PRIVATE)` открывает поток записи во внутреннее хранилище.
3. `MODE_PRIVATE` означает, что файл доступен только этому приложению.
4. После сохранения список обновляется, и пользователь сразу видит результат.
5. Для ввода данных я использовал `AlertDialog`, чтобы не перегружать основной экран лишними полями.

### Что именно я сделал

Я реализовал удобную адаптацию темы внутреннего файлового хранения:

1. Пользователь создает заметку.
2. Задает имя файла.
3. Вводит текст.
4. Файл сохраняется во внутренней памяти приложения.
5. После сохранения файл появляется в списке.

### Чем это отличается от классического примера из методички

В методичке обычно показывается более простой вариант с полем и кнопкой на одном экране. В финальном проекте я сделал более удобный интерфейс:

1. Список файлов находится на основном экране.
2. Создание вынесено в диалог.
3. Вход в создание заметки сделан через `FloatingActionButton`.

При этом базовый принцип из практики остался тем же: запись текстовых данных во внутреннее хранилище через `openFileOutput`.

## Что именно из практики №6 перенесено в финальный проект

В текущем модуле финального проекта реализованы:

1. `SharedPreferences` для сохранения пользовательских данных.
2. Внутреннее файловое хранилище для текстовых заметок.

В этом модуле не выделены отдельные экраны для:
